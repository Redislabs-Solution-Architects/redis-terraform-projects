# Redis Enterprise Monitoring UI + Failover Demo

Single-region Flask app that does two things:

- monitors both Redis Enterprise clusters through their REST APIs
- demonstrates continuous availability with a real `redis-py` `MultiDBClient`

The app prefers the Region 1 public Redis database endpoint, automatically fails over to Region 2 when Region 1 becomes unavailable to this app instance, and automatically fails back when Region 1 is restored.

## What This Module Demonstrates

- Region 1 is the preferred Redis endpoint
- Region 2 is the fallback endpoint
- The app writes and reads a synthetic key through a single failover-aware Redis client
- A simulated Region 1 outage is app-scoped only
- No REC, CRDB, DNS, or ingress resources are modified during the demo

## Architecture

```text
Browser
  -> redis-monitoring-ui service (single region)
      -> Redis Enterprise REST APIs for monitoring
      -> redis-py MultiDBClient for data access
          -> <db-name>-db.region1.<domain>:<port>  preferred
          -> <db-name>-db.region2.<domain>:<port>  fallback
```

## Deployment Model

- The app is deployed in one region only
- It monitors both regions from that single deployment
- It uses the public Redis database endpoints generated by the dual-region ingress/DNS setup
- Outage simulation is internal to the app and only affects this demo client

## Prerequisites

- Both RECs are running
- The Active-Active database already exists
- `post-deployment/config.env` has been generated by Terraform
- `aws`, `kubectl`, and `yq` are installed locally
- The chosen deployment cluster contains the API credential secrets for both regions

## Deploy

```bash
cd redis-enterprise-software/eks-dual-region-active-active/post-deployment/04-redis-monitoring-ui
./deploy.sh
```

Then access it:

```bash
kubectl port-forward -n redis-enterprise svc/redis-monitoring-ui 8080:5000 --context region1
```

Open `http://localhost:8080`.

## Config

User-tunable values live in [config.yaml](./config.yaml).

Important fields:

- `deployment_region`: which cluster runs the app
- `refresh_interval`: dashboard refresh cadence
- `failover.preferred_region`: endpoint preference order
- `failover.*`: redis-py failover timing and circuit-breaker thresholds
- `demo.*`: synthetic workload behavior

Deployment-time values are auto-generated by `deploy.sh`, including:

- database name
- database port
- region1/region2 public Redis endpoints
- region1/region2 REST API endpoints
- accessible monitoring secret names
- optional database password secret name

## Demo Flow

1. Open the UI
2. Click `Start Demo`
3. Confirm the active region is `region1`
4. Click `Simulate Region 1 Outage`
5. Watch the event log and active region switch to `region2`
6. Click `Restore Region 1`
7. Wait for auto failback and confirm the client returns to `region1`

The dashboard continues to show cluster and CRDB state throughout the demo.

## Endpoints

- `GET /` main UI
- `GET /api/cluster/<region>` monitoring data
- `GET /api/database/<region>` database data
- `GET /api/crdb` CRDB comparison
- `GET /api/demo/status` failover demo status
- `POST /api/demo/start` start synthetic workload
- `POST /api/demo/simulate-region1-outage` app-local outage toggle
- `POST /api/demo/restore-region1` clear outage toggle
- `POST /api/demo/reset` reset demo state
- `GET /health` liveness/readiness

## Notes

- Redis client failover uses `redis-py` geographic failover support.
- By default the app uses ping-based health checks.
- Lag-aware health checks are configurable but disabled by default.
- If no database password secret is detected, the demo client connects without Redis auth.
